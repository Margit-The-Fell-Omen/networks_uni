# ОСКС — ЛР №2. Пакетная передача данных

Два экземпляра программы обмениваются сообщениями по COM-порту.
Вариант 1: максимальная длина кадра 100 байт, бит-стаффинг, значения полей
выводятся в двоичном виде.

Здесь описана внутренняя логика: структура кадра, бит-стаффинг и разбиение
сообщения на кадры. Интерфейс (окна) не рассматривается.

## 1. Структура кадра

```
┌──────────────┬───────────┬───────────┬───────────────┬──────┬──────────────────┐
│ Флаг (8)     │ Адрес наз.│ Адрес ист.│ Данные (1..77)│ FCS  │ Резерв (10 нулей)│
│              │   (1)     │   (1)     │   UTF-8       │ (1)  │                  │
└──────────────┴───────────┴───────────┴───────────────┴──────┴──────────────────┘
                             \______________ тело: бит-стаффинг ______________/
```

| Поле | Длина | Сейчас | Назначение |
|---|---|---|---|
| Флаг начала кадра | 8 | `450501-1` | найти начало кадра в потоке |
| Адрес назначения | 1 | `00` | в будущем — кому адресован кадр |
| Адрес источника | 1 | `00` | в будущем — от кого кадр |
| Данные | 1..77 | UTF-8 | текст сообщения |
| FCS | 1 | `00` | в будущем — контрольная сумма |
| Резерв | 10 | `00`×10 | задел + признак конца кадра |

Все шесть полей присутствуют в каждом кадре. Флаг и данные заполняются
реально, остальные поля всегда передаются нулевыми — их смысл пока только
задел на будущее. Единственное поле переменной длины — данные.

Флаг — восемь символов: `45050` + последняя цифра номера группы + `-` + номер
варианта. Для группы 450501 и варианта 1 это `450501-1`:

```
34 35 30 35 30 31 2D 31   (ASCII "450501-1")
```

В битах:

```
00110100 00110101 00110000 00110101 00110000 00110001 00101101 00110001
```

Последние 10 байт кадра — всегда нули. По ним приёмник определяет конец
кадра, поэтому завершающего флага нет: кадр заканчивается нулями.

### Пример кадра с одним байтом данных ("A")

```
34 35 30 35 30 31 2D 31 | 00 00 41 | 00 | 00 00 00 00 00 00 00 00 00 00
└──────── флаг ────────┘  dest src  fcs  └────────── резерв ──────────┘
```

Заметьте: после данных идут **11** нулей — один `00` принадлежит FCS, десять —
резерву. Это важно для приёмника (см. раздел 3).

### Ограничение длины

Длина кадра без стаффинга:

```
8 (флаг) + 1 + 1 + N + 1 + 10 = 21 + N байт
```

При N = 77 получается 98 байт, бит-стаффинг добавляет максимум 2 байта —
итого ровно 100, то есть предел варианта 1. Поэтому `MAX_DATA_LEN = 77`:
это максимальный размер поля данных, при котором кадр ещё влезает в лимит.

## 2. Бит-стаффинг

Задача — не дать последовательности флага случайно появиться внутри кадра,
иначе приёмник примет её за начало следующего кадра.

Флаг передаётся как есть. Тело (адреса, данные, FCS, резерв) превращается в
биты и просматривается окном в 63 бита. После добавления очередного бита
окно сравнивается с первыми 63 битами флага (то есть с флагом без последнего
бита). Если совпало, следующий бит замкнул бы флаг, поэтому в поток
вставляется бит, противоположный последнему биту флага. У флага последний
бит равен 1, значит вставляется 0.

Свойства:

- после вставки окно уже не совпадает с префиксом флага, поэтому двух
  вставок подряд быть не может;
- вставка нужна только при реальном появлении 63-битного префикса, для
  текста это практически никогда — количество вставок минимально;
- упаковка битов в байты идёт от старшего бита к младшему, хвост последнего
  байта добивается нулями.

Приёмник делает обратное: ведёт такое же окно и после совпадения пропускает
следующий бит. Хвостовые биты, не составившие целый байт, отбрасываются.

## 3. Приём кадра

Приёмник (`frame::Receiver`) накапливает байты в буфере и работает так:

1. Ищет в буфере флаг. Всё, что стоит до флага, — мусор, он отбрасывается
   (последние 7 байт сохраняются: флаг мог прийти не целиком).
2. После флага ищет последовательность нулей длиной не меньше 10. Конец
   кадра — конец этой последовательности.
3. Выполняет `destuff` тела между флагом и найденным концом.
4. Разбирает тело (`parseBody`):
   - `dataLen = размер тела - 13` (2 адреса + FCS + 10 резерва);
   - проверяет, что `dataLen` в пределах 1..77;
   - проверяет, что последние 10 байт действительно нули.
5. Сбойный кадр просто пропускается, разбор продолжается со следующего флага.

Почему берётся именно **конец** нулевой последовательности, а не первые
десять нулей: FCS сейчас равен нулю и сливается с резервом, в конце кадра
получается 11 нулей подряд. Если отрезать по первым десяти, последний байт
данных уедет в FCS и потеряется. Если буфер оборвался ровно на десяти нулях,
приёмник ждёт ещё байт: последовательность может продолжиться.

Кадр не содержит поля длины: его длина определяется позицией нулей резерва.
Поэтому данные не могут содержать десять нулевых байт подряд — для текста в
UTF-8 это невозможно.

Отдельной операции «завершить поток» тоже нет: нули приходят в составе самого
кадра, поэтому кадр отдаётся сразу, как только они получены.

## 4. Разбиение сообщения на кадры

Одно сообщение — одна строка, отправляемая по Enter. В поле данных одного
кадра помещается максимум 77 байт, поэтому длинное сообщение режется на
несколько кадров.

Алгоритм (`SendLine` в `main.cpp`):

1. к тексту сообщения добавляется символ возврата каретки `\r`;
2. текст посимвольно переводится в UTF-8;
3. байты копятся в буфере; если добавление очередного символа превысило бы
   77 байт, текущий буфер отправляется одним кадром и начинается новый;
4. после цикла остаток буфера отправляется последним кадром.

Примеры (ASCII, один байт на символ):

- сообщение 100 символов → 100 + 1 (`\r`) = 101 байт → два кадра: 77 и 24;
- сообщение 77 символов → 78 байт → два кадра: 77 и 1 (во втором кадре только `\r`);
- сообщение короче 77 символов → один кадр.

Границы кадров никогда не разрывают многобайтовый символ UTF-8: текст
переводится в байты по одному символу, и проверка длины стоит до добавления
символа.

Каждый кадр отправляется сразу и целиком: флаг, тело, 10 нулей. Завершающего
флага нет, кадры идут в линию подряд. Приёмник обрабатывает их по очереди и
дописывает данные в окно вывода, поэтому разрезанное сообщение выглядит
цельным. На уровне кадров границы сообщений не передаются: разделителем
служит `\r` в конце данных, который при выводе превращается в перевод строки.

## 5. Путь сообщения целиком

```
отправка:  текст → + \r → UTF-8 → нарезка по 77 байт → serializeBody
           → бит-стаффинг → COM-порт

приём:     COM-порт → Receiver: флаг → нули резерва → destuff → parseBody
           → UTF-8 → окно вывода
```

## 6. Задел на будущее (для отчёта)

- **Адрес назначения** — фильтрация чужих кадров, если на линии несколько
  станций: `if (f.destination != MY_ADDR) return;`
- **Адрес источника** — ответ или подтверждение: отправить кадр обратно на
  `f.source`.
- **FCS** — CRC-8 по полям от адреса назначения до данных; при несовпадении
  кадр отбрасывается, чтобы сбой не попал в текст.
- **Резерв** — сейчас это признак конца кадра. Занимать эти десять байт
  чем-то другим можно только после того, как конец кадра начнёт определяться
  иначе (например, по полю длины), иначе приёмник перестанет находить конец.

## 7. Где что лежит

| Файл | Содержимое |
|---|---|
| `frame.h`, `frame.cpp` | структура кадра, сборка/разбор тела, стаффинг, приёмник |
| `serial.cpp` | работа с COM-портом (открытие, приём, передача) |
| `main.cpp` | отправка сообщения (`SendLine`, `SendFrameData`), обработка принятых кадров |

Ключевые функции:

- `serializeBody` — поля кадра в байты: адрес, адрес, данные, FCS, резерв;
- `parseBody` — обратный разбор с проверкой длины и нулевого резерва;
- `stuff` / `destuff` — бит-стаффинг и восстановление;
- `Receiver::feed` — сборка кадров из потока байт;
- `SendLine` — нарезка сообщения на кадры, `SendFrameData` — сборка и отправка
  одного кадра.

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release

```

## 9. Ограничения

- Полезная нагрузка — текст UTF-8; десять нулевых байт в данных были бы
  приняты за конец кадра.
- Конец кадра ищется по байтам, поэтому предполагается, что стаффинг не
  сдвигает поток на нецелое число байт. При 63-битном триггере вставок
  практически не бывает, так что это выполняется.
- Подтверждений и повторной передачи нет: сбойный кадр просто теряется.
