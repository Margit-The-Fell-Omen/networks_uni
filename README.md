# ОСКС — ЛР №3. Канальное кодирование

Два экземпляра программы обмениваются сообщениями по COM-порту.
Вариант 1: циклический код, вероятность ошибки 10 %, максимальная длина
кадра 100 байт, бит-стаффинг.

Здесь описана внутренняя логика: структура кадра, расчёт FCS, эмуляция
ошибок, бит-стаффинг, приём и разбиение сообщения на кадры. Интерфейс
(окна) не рассматривается.

## 1. Структура кадра

```
┌──────────────┬───────────────┬──────────────────┬───────────────┬────────┬──────────────────┐
│ Флаг (8)     │ Начало сообщ. │ Осталось кадров  │ Данные (1..77)│ FCS(2) │ Резерв (9 нулей) │
│              │      (1)      │       (1)        │   UTF-8       │        │                  │
└──────────────┴───────────────┴──────────────────┴───────────────┴────────┴──────────────────┘
                                 \________________ тело: бит-стаффинг ________________/
```

| Поле | Длина | Сейчас | Назначение |
|---|---|---|---|
| Флаг начала кадра | 8 | `450501-1` | найти начало кадра в потоке |
| Флаг начала сообщения | 1 | `00` | в будущем 1 — первый кадр сообщения |
| Осталось кадров | 1 | `00` | в будущем — сколько кадров осталось (N..1) |
| Данные | 1..77 | UTF-8 | текст сообщения |
| FCS | 2 | CRC-16 | циклический код только от поля данных |
| Резерв | 9 | `00`×9 | задел + признак конца кадра |

Все шесть полей присутствуют в каждом кадре. Флаг и данные заполняются
реально, FCS считается по данным, поля `messageStart` и `framesLeft` пока
передаются нулевыми — их смысл задел на будущее. Единственное поле
переменной длины — данные.

Флаг — восемь символов: `45050` + последняя цифра номера группы + `-` + номер
варианта. Для группы 450501 и варианта 1 это `450501-1`:

```
34 35 30 35 30 31 2D 31   (ASCII "450501-1")
```

В битах:

```
00110100 00110101 00110000 00110101 00110000 00110001 00101101 00110001
```

Кадр заканчивается девятью зарезервированными нулями: по ним приёмник
находит конец кадра, поэтому завершающего флага нет.

### Пример кадра с одним байтом данных ("A")

```
34 35 30 35 30 31 2D 31 | 00 00 41 | 58 E5 | 00 00 00 00 00 00 00 00 00
└──────── флаг ────────┘  нач. ост.  данные   FCS    └──────── резерв ────────┘
```

FCS для `"A"` равен `58 E5`, весь кадр занимает 22 байта.

### Ограничение длины

Длина кадра без стаффинга:

```
8 (флаг) + 1 + 1 + N + 2 + 9 = 21 + N байт
```

При N = 77 получается 98 байт, бит-стаффинг добавляет максимум 2 байта — итого ровно 100, то есть предел
варианта 1. Поэтому `MAX_DATA_LEN = 77`; это проверяется `static_assert`
в `frame.h`.

### Почему резервных байтов девять, а не десять

В ЛР2 резерв занимал 10 байт. В ЛР3 появилось поле FCS, и по заданию его
длину нужно рассчитать, а при нехватке байтов — занять часть резерва.
Расчёт даёт два байта FCS, поэтому один байт резерва уходит под второй байт
контрольной суммы: 10 − 1 = 9. Общая длина кадра при этом не изменилась.

## 2. Поле FCS

FCS — циклический код (CRC-16/CCITT), считается **только по полю данных**.
Параметры: образующий многочлен `g(x) = x^16 + x^12 + x^5 + 1` (`0x1021`),
начальное значение `0x0000`, старший бит вперёд, без отражения.

Расчёт минимальной длины:

```
k = MAX_DATA_LEN * 8 = 77 * 8 = 616 бит   - максимальная длина данных
код должен исправлять одиночные ошибки, значит все n = k + r позиций
должны давать разные ненулевые синдромы: 2^r >= k + r + 1
r = 9:  2^9  = 512  <  616 + 9  + 1 = 626  - не хватает
r = 10: 2^10 = 1024 >= 616 + 10 + 1 = 627  - хватает
округляем до байтов: ceil(10 / 8) = 2 байта
```

Период многочлена `p(x) = g(x) / (x + 1)` равен 32767, что больше длины
кодового слова `n = 632`, поэтому одиночная ошибка в любой позиции даёт
уникальный синдром.

Исправление одиночной ошибки сделано «в лоб», как перебор: `crc::CorrectData`
по очереди инвертирует каждый бит данных и пересчитывает CRC; если сумма
совпала с принятой — ошибка найдена и данные исправлены. Для 77 байт это
616 вариантов, для лабораторной работы вполне приемлемо.

## 3. Бит-стаффинг

Задача — не дать последовательности флага случайно появиться внутри кадра,
иначе приёмник примет её за начало следующего кадра.

Флаг передаётся как есть. Тело (все поля, включая FCS и резерв) превращается
в биты и просматривается окном в 63 бита. После добавления очередного бита
окно сравнивается с первыми 63 битами флага (то есть с флагом без последнего
бита). Если совпало, следующий бит замкнул бы флаг, поэтому в поток
вставляется бит, противоположный последнему биту флага. У флага последний
бит равен 1, значит вставляется 0.

Упаковка битов в байты идёт от старшего бита к младшему, хвост последнего
байта добивается нулями. Приёмник делает обратное: ведёт такое же окно и
после совпадения пропускает следующий бит.

FCS считается до стаффинга: стаффинг применяется к кадру, в котором FCS уже
заполнен, как и требует задание.

## 4. Эмуляция ошибок

Перед передачей каждого кадра с вероятностью `ERROR_PERCENT` (для варианта 1
— 10 %) искажается один случайный бит в одном случайном байте поля данных.
Ошибка вносится после расчёта FCS, поэтому контрольная сумма её обнаруживает.

`injectError` возвращает информацию об ошибке (номер байта и бита), чтобы
окно состояния могло показать кадр после эмуляции ошибки и подчеркнуть
искажённый бит. При приёме `crc::IsCorrect` проверяет FCS и исправляет
одиночную ошибку; если ошибка не исправляется, данные остаются как есть.

## 5. Приём кадра

Приёмник (`frame::Receiver`) накапливает байты в буфере и работает так:

1. Ищет в буфере флаг. Всё, что стоит до флага, — мусор, он отбрасывается
   (последние 7 байт сохраняются: флаг мог прийти не целиком).
2. После флага ищет последовательность нулей длиной не меньше 9. Конец
   кадра — конец этой последовательности.
3. Выполняет `destuff` тела между флагом и найденным концом.
4. Разбирает тело (`parseBody`):
   - `dataLen = размер тела - 13` (`messageStart` + `framesLeft` + FCS + 9 резерва);
   - проверяет, что `dataLen` в пределах 1..77;
   - проверяет, что последние 9 байт действительно нули.
5. Возвращает кадр; проверка и исправление FCS выполняются при обработке
   принятого кадра. Сбойный кадр не попадает в текст.

Почему берётся именно **конец** нулевой последовательности, а не первые
девять нулей: FCS — это произвольные два байта, и они тоже могут быть
нулевыми. Если FCS кончается нулём, он сливается с резервом, и нулей подряд
получается больше девяти. Кадр заканчивается там, где заканчивается вся
последовательность, а не через девять байт от её начала.

### Подтверждение конца последнего кадра

Если нули доходят до конца буфера, неизвестно, закончилась ли
последовательность: следующий байт (флаг следующего кадра) ещё не пришёл.
Ждать его для последнего кадра нельзя — следующая передача может быть
нескоро. Поэтому используется таймаут:

- в окне вывода стоит таймер на 20 мс;
- он вызывает `Receiver::flush(120)`;
- если с последнего принятого байта прошло не меньше 120 мс, нулевая
  последовательность считается законченной и кадр отдаётся.

Кадры, за которыми сразу идёт следующий флаг, отдаются без задержки. Таймаут
работает только для последнего кадра сообщения.

Проверять конец по FCS нельзя: префикс кадра без последнего нуля резерва сам
может оказаться корректным кадром с более коротким полем данных — CRC такое
не различает.

## 6. Разбиение сообщения на кадры

Одно сообщение — одна строка, отправляемая по Enter. В поле данных одного
кадра помещается максимум 77 байт, поэтому длинное сообщение режется на
несколько кадров.

Алгоритм (`SendLine` в `main.cpp`):

1. к тексту сообщения добавляется символ возврата каретки `\r`;
2. текст посимвольно переводится в UTF-8;
3. байты копятся в буфере; если добавление очередного символа превысило бы
   77 байт, текущий буфер отправляется одним кадром и начинается новый;
4. после цикла остаток буфера отправляется последним кадром.

Примеры (ASCII, один байт на символ):

- сообщение 100 символов → 100 + 1 (`\r`) = 101 байт → два кадра: 77 и 24;
- сообщение 77 символов → 78 байт → два кадра: 77 и 1 (во втором кадре только `\r`);
- сообщение короче 77 символов → один кадр.

Границы кадров не разрывают многобайтовый символ UTF-8: текст переводится
в байты по одному символу, и проверка длины стоит до добавления символа.

Каждый кадр отправляется сразу и целиком: флаг, тело, 9 нулей. Завершающего
байта нет, кадры идут в линию подряд. Приёмник обрабатывает их по очереди,
поэтому разрезанное сообщение собирается обратно. На уровне кадров границы
сообщений не передаются: разделителем служит `\r` в конце данных, который
при выводе превращается в перевод строки.

## 7. Путь сообщения целиком

```
отправка:  текст → + \r → UTF-8 → нарезка по 77 байт → serializeBody
           → расчёт FCS → бит-стаффинг → эмуляция ошибки → COM-порт

приём:     COM-порт → Receiver: флаг → нули резерва → destuff → parseBody
           → проверка/исправление FCS → UTF-8 → окно вывода
```

## 8. Задел на будущее (для отчёта)

- **Флаг начала сообщения** — 1 у первого кадра сообщения, 0 у остальных;
  позволит приёмнику понимать, где начинается новое сообщение, и сбрасывать
  недособранный хвост.
- **Осталось кадров** — N..1; по нему видно, когда сообщение закончилось,
  и можно заметить потерю кадра.
- **FCS** — уже используется: CRC-16, обнаружение и исправление одиночных
  ошибок.
- **Резерв** — сейчас это признак конца кадра. Занимать эти девять байт
  чем-то другим можно только после того, как конец кадра начнёт определяться
  иначе (например, по полю длины), иначе приёмник перестанет находить конец.

## 9. Где что лежит

| Файл | Содержимое |
|---|---|
| `frame.h`, `frame.cpp` | структура кадра, FCS, эмуляция ошибок, стаффинг, приёмник |
| `serial.cpp` | работа с COM-портом (открытие, приём, передача) |
| `main.cpp` | отправка сообщения (`SendLine`, `SendFrameData`), обработка принятых кадров |

Ключевые функции:

- `serializeBody` — поля кадра в байты: начало, осталось, данные, FCS, резерв;
- `parseBody` — обратный разбор с проверкой длины и нулевого резерва;
- `crc::calculateFCS` / `crc::setFCS` — расчёт CRC-16 по данным;
- `crc::IsCorrect` — проверка и исправление одиночной ошибки;
- `injectError` — эмуляция ошибки перед передачей;
- `stuff` / `destuff` — бит-стаффинг и восстановление;
- `Receiver::feed` / `flush` — сборка кадров из потока байт и таймаут последнего кадра;
- `SendLine` — нарезка сообщения на кадры, `SendFrameData` — сборка и отправка
  одного кадра.

## 11. Ограничения

- Полезная нагрузка — текст UTF-8; девять нулевых байт в данных были бы
  приняты за конец кадра.
- Последний кадр отдаётся по таймауту 120 мс, кадры с продолжением — сразу.
- Исправляются только одиночные ошибки; более серьёзное искажение остаётся
  в данных (кадр при этом не теряется, но и не восстанавливается).
- Подтверждений и повторной передачи нет.
