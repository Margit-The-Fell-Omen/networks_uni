# ОСКС — ЛР №4. Методы доступа к моноканалу

Два экземпляра программы обмениваются сообщениями по COM-порту.
Вариант 1: занятость канала 10 %, коллизия 40 %, коллизия в отношении
отдельного байта, jam-сигнал. База — программа ЛР3: циклический код,
эмуляция ошибок 10 %, максимальная длина кадра 100 байт, бит-стаффинг.

Здесь описана внутренняя логика: структура кадра, FCS, бит-стаффинг,
приём, разбиение сообщения на кадры и алгоритм CSMA/CD. Интерфейс (окна)
не рассматривается.

## 1. Структура кадра

```
┌──────────────┬───────────────┬──────────────────┬───────────────┬────────┬──────────────────┐
│ Флаг (8)     │ Начало сообщ. │ Осталось кадров  │ Данные (1..77)│ FCS(2) │ Резерв (9 нулей) │
│              │      (1)      │       (1)        │   UTF-8       │        │                  │
└──────────────┴───────────────┴──────────────────┴───────────────┴────────┴──────────────────┘
                                 \________________ тело: бит-стаффинг ________________/
```

| Поле | Длина | Сейчас | Назначение |
|---|---|---|---|
| Флаг начала кадра | 8 | `450501-1` | найти начало кадра в потоке |
| Флаг начала сообщения | 1 | `00` | в будущем 1 — первый кадр сообщения |
| Осталось кадров | 1 | `00` | в будущем — сколько кадров осталось (N..1) |
| Данные | 1..77 | UTF-8 | текст сообщения |
| FCS | 2 | CRC-16 | циклический код только от поля данных |
| Резерв | 9 | `00`×9 | задел + признак конца кадра |

Все шесть полей присутствуют в каждом кадре. Флаг и данные заполняются
реально, FCS считается по данным, поля `messageStart` и `framesLeft` пока
передаются нулевыми. Единственное поле переменной длины — данные.

Флаг — восемь символов: `45050` + последняя цифра номера группы + `-` + номер
варианта. Для группы 450501 и варианта 1 это `450501-1`:

```
34 35 30 35 30 31 2D 31   (ASCII "450501-1")
```

Кадр заканчивается девятью зарезервированными нулями, завершающего флага нет.

### Пример кадра с одним байтом данных ("A")

```
34 35 30 35 30 31 2D 31 | 00 00 41 | 58 E5 | 00 00 00 00 00 00 00 00 00
└──────── флаг ────────┘  нач. ост.  данные   FCS    └──────── резерв ────────┘
```

FCS для `"A"` равен `58 E5`, весь кадр занимает 22 байта.

### Ограничение длины

Длина кадра без стаффинга:

```
8 (флаг) + 1 + 1 + N + 2 + 9 = 21 + N байт
```

При N = 77 получается 98 байт, бит-стаффинг добавляет максимум 2 байта —
итого ровно 100, то есть предел варианта 1. Поэтому `MAX_DATA_LEN = 77`;
это проверяется `static_assert` в `frame.h`.

### Почему резервных байтов девять, а не десять

По заданию ЛР3 длину FCS нужно рассчитать, а при нехватке байтов — занять
часть резерва. Расчёт даёт два байта FCS, поэтому один байт резерва уходит
под второй байт контрольной суммы: 10 − 1 = 9.

## 2. Поле FCS

FCS — циклический код (CRC-16/CCITT), считается **только по полю данных**:
`g(x) = x^16 + x^12 + x^5 + 1` (`0x1021`), начальное значение `0x0000`,
старший бит вперёд, без отражения.

```
k = MAX_DATA_LEN * 8 = 77 * 8 = 616 бит
2^r >= k + r + 1
r = 9:  2^9  = 512  <  616 + 9  + 1 = 626  - не хватает
r = 10: 2^10 = 1024 >= 616 + 10 + 1 = 627  - хватает
ceil(10 / 8) = 2 байта
```

Исправление одиночной ошибки: `crc::CorrectData` перебирает инверсии
отдельных битов данных и сравнивает пересчитанную FCS с принятой. Если
совпало — ошибка найдена и исправлена.

## 3. Бит-стаффинг

Флаг передаётся как есть. Тело (все поля, включая FCS и резерв) превращается
в биты и просматривается окном в 63 бита. Если после добавления очередного
бита окно совпало с первыми 63 битами флага, следующий бит замкнул бы флаг,
поэтому вставляется бит, противоположный последнему биту флага (у флага
последний бит 1, значит вставляется 0).

Биты упаковываются в байты от старшего к младшему, хвост последнего байта
добивается нулями. Приёмник ведёт такое же окно и после совпадения
пропускает следующий бит. Стаффинг применяется к кадру с уже заполненным FCS.

## 4. Эмуляция ошибок

Как в ЛР3: перед передачей каждого кадра с вероятностью 10 % искажается
один случайный бит в одном случайном байте поля данных. Ошибка вносится
после расчёта FCS, поэтому контрольная сумма её обнаруживает и исправляет.
Эмуляция ошибок и эмуляция моноканала включаются независимо.

## 5. Приём кадра

1. Приёмник накапливает байты и ищет флаг; мусор до флага отбрасывается
   (последние 7 байт сохраняются: флаг мог прийти не целиком).
2. После флага ищет последовательность нулей длиной не меньше 9. Конец
   кадра — конец этой последовательности.
3. Выполняет `destuff` тела между флагом и найденным концом.
4. Разбирает тело: `dataLen = размер тела - 13` (2 служебных поля + FCS + 9
   резерва), проверяет `dataLen` в пределах 1..77 и что последние 9 байт —
   нули.
5. Проверяет FCS. Кадр, разрушенный коллизией, её не проходит и
   отбрасывается; одиночная ошибка исправляется.

Конец берётся по **концу** нулевой последовательности, а не по первым девяти
нулям: FCS — произвольные байты и тоже может кончаться нулём, тогда нулей
подряд получается больше девяти.

### Последний кадр и таймаут

Если нули доходят до конца буфера, неизвестно, закончилась ли
последовательность: следующий байт ещё не пришёл. Для последнего кадра
ждать нечего, поэтому окно вывода раз в 20 мс вызывает `Receiver::flush(120)`:
если с последнего принятого байта прошло не меньше 120 мс, кадр считается
законченным. Кадры, за которыми сразу идёт следующий флаг, отдаются без
задержки.

### Ресинхронизация после коллизии

При коллизии передатчик обрывает кадр на выбранном байте, отправляет
jam-сигнал и позже повторяет кадр целиком. Приёмник видит обрывок, jam и
новый флаг. Если кадр не разобрался или не прошёл FCS, приёмник ищет внутри
уже принятого куска флаг следующей попытки и начинает разбор заново с него.
Поэтому повторный кадр принимается, а обрывок отбрасывается.

## 6. Разбиение сообщения на кадры

Одно сообщение — одна строка, отправляемая по Enter. В поле данных одного
кадра помещается максимум 77 байт, поэтому длинное сообщение режется на
несколько кадров (`SendLine`):

1. к тексту добавляется `\r`;
2. текст посимвольно переводится в UTF-8;
3. если добавление очередного символа превысило бы 77 байт, текущий буфер
   отправляется кадром и начинается новый;
4. остаток отправляется последним кадром.

Примеры: 100 символов → 101 байт с `\r` → кадры 77 и 24; 77 символов →
кадры 77 и 1 (во втором только `\r`).

Границы кадров не разрывают многобайтовый символ UTF-8. Каждый кадр
отправляется целиком (флаг, тело, 9 нулей); разделителем сообщений служит
`\r` в конце данных, который при выводе превращается в перевод строки.

## 7. CSMA/CD

Эмуляция моноканала — в `channel.cpp`. Параметры варианта 1:

| Параметр | Значение |
|---|---|
| Вероятность занятости канала | 10 % |
| Вероятность коллизии | 40 % |
| Коллизия | в отношении отдельного байта |
| Jam-сигнал | 4 байта `0xFF` |
| Слот времени | 50 мс |
| Ожидание занятого канала | 10 мс |
| Максимум попыток | 16 |

Состояния (`channel::Session`): `Idle → Listening → Transmitting → Done`,
с ветками `Busy`, `Collision`, `Jam`, `Backoff`, `Error`, `Cancelled`.

Порядок работы:

1. **Прослушивание.** С вероятностью 10 % канал занят: передатчик ждёт 10 мс
   и слушает снова.
2. **Передача.** С вероятностью 40 % на попытку случается коллизия; заранее
   выбирается байт, на котором она произойдёт. Кадр отправляется кусками
   (размер куска зависит от скорости порта, 1..16 байт), чтобы состояние
   успевало обновляться; распараллеливания нет — всё идёт по тикам таймера.
3. **Коллизия.** Передача обрывается на выбранном байте, в порт уходит
   jam-сигнал `FF FF FF FF`, состояние меняется на `Jam`.
4. **Случайная задержка.** Стандартная двоичная экспоненциальная пауза:
   после n-й коллизии `k = random(0 .. 2^n - 1)`, задержка `k * 50 мс`
   (n не больше 10). После паузы — снова прослушивание и повтор.
5. После 16 коллизий передача считается неудачной (`Error`).

В окне состояния показываются состояние канала, число попыток, коллизий и
ожиданий канала, а по каждой коллизии последнего кадра — символ `*`.

## 8. Путь сообщения целиком

```
отправка:  текст → + \r → UTF-8 → нарезка по 77 байт → serializeBody
           → FCS → бит-стаффинг → эмуляция ошибки → CSMA/CD → COM-порт

приём:     COM-порт → Receiver: флаг → нули резерва → destuff → parseBody
           → FCS (исправление/отбрасывание) → UTF-8 → окно вывода
```

## 9. Задел на будущее (для отчёта)

- **Флаг начала сообщения** — 1 у первого кадра сообщения, 0 у остальных:
  приёмник сможет понимать, где начинается новое сообщение.
- **Осталось кадров** — N..1: видно, когда сообщение закончилось, и можно
  заметить потерю кадра.
- **FCS** — уже используется: CRC-16, обнаружение и исправление одиночных
  ошибок.
- **Резерв** — сейчас признак конца кадра. Занимать эти девять байт
  чем-то другим можно только после смены способа определения конца кадра.

## 10. Где что лежит

| Файл | Содержимое |
|---|---|
| `frame.h`, `frame.cpp` | структура кадра, FCS, эмуляция ошибок, стаффинг, приёмник |
| `channel.h`, `channel.cpp` | эмуляция моноканала и CSMA/CD |
| `serial.cpp` | работа с COM-портом |
| `main.cpp` | отправка сообщения, очередь кадров, обработка принятых кадров |

Ключевые функции:

- `serializeBody` / `parseBody` — сборка и разбор тела кадра;
- `crc::calculateFCS` / `crc::setFCS` / `crc::IsCorrect` — CRC-16 и исправление;
- `injectError` — эмуляция ошибки;
- `stuff` / `destuff` — бит-стаффинг;
- `Receiver::feed` / `flush` — сборка кадров и таймаут последнего кадра;
- `channel::Session::tick` — шаг CSMA/CD;
- `SendLine` / `SendFrameData` — нарезка сообщения и постановка кадров в очередь.

## 12. Ограничения

- Полезная нагрузка — текст UTF-8; девять нулевых байт в данных были бы
  приняты за конец кадра.
- Последний кадр отдаётся по таймауту 120 мс.
- Исправляются только одиночные ошибки; кадр, разрушенный коллизией,
  отбрасывается и принимается только при повторной передаче.
- Подтверждений на уровне протокола нет: надёжность обеспечивает только
  повторная передача в CSMA/CD.
